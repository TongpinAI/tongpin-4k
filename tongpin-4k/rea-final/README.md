# 同频4K 成品代码验证

构建并完成官方 AAPT、APK 签名和对齐验证后，传入最终 APK 的 SHA-256 再运行：

```powershell
node .\tongpin-4k\rea-final\verify-final.mjs <最终APK的64位小写SHA256>
```

脚本先核对固定目标 `tongpin-4k/output/tongpin-4k-1.0.0.apk` 的摘要，再启动一个 REA 6.7.0 / JADX 0.7.1 provider。它不修改应用源码，且会关闭 provider。方法输出按类名与方法名的 UTF-8 十六进制命名，避免 Windows 大小写冲突。

验证范围：独立启动页的更新/图片/推广/SDK 开屏入口关闭，正常初始化与子协程仍在，个人页仅 Banner 加载方法为空而签到方法仍有实现，视频选择/去广告逻辑，以及 4K 最新集选择和集号匹配。每份证据核对精确方法名、DEX 描述符、方法体完整性和最终 APK 摘要。通过后才写入 `verification.json`。

JADX 会把协程的公共出口复制到多个 Java switch 分支。唯一首页调用数量由 `CheckStartupDex.java` 使用同一 JADX JAR 的 dexlib2 读取成品 DEX 指令核对，结果在 `startup-dex-calls.json`；不把反编译文本的重复块当成多个真实调用。

REA 的 APK manifest 查询存在选中库 manifest 的已知问题，本脚本不调用该接口。包名、版本、图标、资源和 APK 签名由主任务的官方工具链检查，不将方法签名检查表述为 APK 签名验证。

## 尚需运行验证的关键风险

- 新包名和签名下，原服务或第三方 SDK 是否继续允许初始化、登录与请求，需要设备验证；新应用不会自动继承旧包数据。
- 冷启动、条款同意/拒绝、权限拒绝、网络超时以及后台恢复时，协程能否顺利进入首页，静态代码检查无法替代实际操作。
- 4K 和最新集判断依据上游线路标签、集标题和非空 URL；它不证明实际分辨率、远程 URL 可播性、片源更新速度或各线路集名一致。
- 4K/HDR 编解码、不同 Android 版本、设备能力与带宽会影响实际播放；未执行手机播放测试。
- 所列广告入口的代码已被检查，仍需在真实远程配置、导航、签到及重播场景确认展示行为；签到及其他保留功能没有被全局删除。
- 上游条款、隐私与联系仍属于真实上游主体，远程内容可变化；本地定制版更新入口关闭，后续版本需要自行分发并持续使用自己的签名。
